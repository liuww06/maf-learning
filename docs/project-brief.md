# 研发知识与故障排查助手

面向维护 .NET 后端服务的研发人员，帮助他们从运行手册和服务数据中找到证据、组织诊断、形成处置方案，并在人工审批后创建模拟工单。整个项目从命令行开始，最终通过 ASP.NET Core 提供服务。

## 一个完整任务

用户输入：“订单服务刚发版，延迟升高了。请检查相关信息，给出排查建议，需要处理时先让我确认。”

应用查询虚构的发布记录和指标，检索故障手册，区分观察到的事实与待验证假设，输出诊断依据和下一步建议。如果需要工单，先展示内容和操作范围，等待人确认后写入本地模拟工单存储，并返回可追踪的编号。

初期使用 [练习数据](../fixtures/README.md)。所有服务、事件和指标均为虚构。实际重启、发布和生产系统访问不属于本项目默认行为。

## 逐步可用的三个版本

| 版本 | 用户获得的价值 | 主要能力 |
| --- | --- | --- |
| V1 知识助手 | 找到当前运行手册并获得带引用的回答，资料不足时明确说明 | 单 Agent、会话、检索、引用、评测 |
| V2 诊断助手 | 联合服务状态、发布信息和文档给出有证据的建议 | 工具调用、结构化输出、显式工作流 |
| V3 协作助手 | 审批后创建模拟工单，断线或重启后继续任务 | 人工参与、checkpoint、幂等、追踪、API 服务 |

这种演进让每个版本都能独立演示，也让新增复杂度有明确的业务原因。

## 初始工具契约

| 工具 | 输入 | 输出 | 行为约束 |
| --- | --- | --- | --- |
| SearchRunbooks | query、service、topK | documentId、revision、section、evidenceText | 必须保留引用来源；过滤条件在代码中实施 |
| GetServiceHealth | serviceId、environment | status、observedAt、evidenceId | 只查询固定的模拟数据；未知服务明确报错 |
| GetRecentDeployments | serviceId、时间范围 | 版本、时间、变更摘要 | 时间范围有界；没有记录时返回空结果 |
| GetMetrics | serviceId、时间范围、指标名 | 数值、单位、时间戳 | 验证参数，不允许模型自行编造数据 |
| CreateIncidentDraft | 摘要、证据、建议 | 可预览的草稿 | 不写入正式工单存储 |
| SubmitIncident | draftId、approvalId、idempotencyKey | incidentId、创建状态 | 由宿主验证身份、审批范围和幂等性后写入模拟存储 |

工具名称和字段是本项目设计，不是声称 MAF 自带这些业务工具。实现时先做查询，再做写入。模型可以提出工具请求，是否允许和如何执行由运行时与应用代码决定。

## 诊断输出

结果至少包含：`summary`、`observations`、`hypotheses`、`evidenceRefs`、`nextChecks`、`proposedAction` 和 `needsApproval`。

`observations` 必须可追溯到文档或工具返回；`hypotheses` 明确待验证。生成符合 JSON schema 的结果不代表事实正确，还要校验证据、业务约束和审批规则。不要求模型输出隐藏思维链；调试依据使用可见消息、工具事件和状态转换。

## 技术实现顺序

1. 控制台、一个 provider、普通响应和流式响应。
2. 纯 C# 模拟查询工具；脚本化响应验证工具协议，真实模型验证选择行为。
3. 会话与本地持久化，先厘清历史和业务状态的所有权。
4. Markdown 文档检索：关键词基线 → embedding 对照 → 有需要时加入混合检索和 rerank。
5. 显式诊断工作流，保留取消、错误和人工介入分支。
6. 使用合适的持久化存储实现审批与恢复，再接入 ASP.NET Core 和追踪。

存储和模型 provider 在对应课程通过小实验选择。不要提前引入大量基础设施。在线调用能力先做探测：文本、流式、工具、结构化输出、用量报告逐项记录；“接口兼容”不能替代能力验证。

## 评测设计

[起始用例](../evals/starter-cases.json) 是 12 条开发用例的种子，覆盖知识回答、信息不足、工具、会话和可靠性，目前没有执行结果。它们不是独立保留集。

L04 前扩充到至少 40 条用例，其中至少 20 条保留为独立评估集；调试使用开发集。反复根据保留集优化后，该集合也成为开发数据，需要新增独立集合。

| 指标 | 计算方式或判定 | 初始验收目标 |
| --- | --- | --- |
| 任务成功率 | 满足用例全部必要条件的运行数 / 运行总数 | 保留集至少 85%，同时列出失败类型 |
| 检索 Recall@k | 检索到的标注相关片段数 / 全部标注相关片段数，按问题汇总 | 先测基线，再解释方案变化 |
| 引用有效性 | 引用存在、版本正确且确实支持对应断言 | 每个评测答案逐项核验 |
| 权限与审批 | 未授权、被拒绝、参数变更后无效审批是否阻止副作用 | 已定义的确定性用例全部通过 |
| 幂等与恢复 | 重放和故障注入后业务记录是否重复，状态是否一致 | 已定义的故障点用例全部通过 |
| 效率 | 总耗时、首事件耗时、模型与工具调用数、输入输出 token | 同环境对比 p50、p95 和总样本量 |
| 成本 | 可用的 provider 用量 × 实验时核对的单价 | 先记录实测基线，再按预算设上限 |

真实模型用例至少重复 3 次，保存模型标识、参数、包版本、提示版本、数据版本和执行时间。小样本的 p95 和成功率仅描述本次实验。模型裁判可辅助评分，关键业务正确性和安全断言需要规则或人工复核。

85% 是本课程的初始目标，不是已达到的结果，也不是通用行业标准。单次调用、整个任务、重试和评测批次均应设预算。token 用量缺失时标为不可用，不能把缺失值当成零。

## 必做失败实验

- 模型请求不存在的工具，或传入错误类型和越界参数。
- 工具超时、返回空数据、出现可重试错误或永久错误。
- 文档过期、互相冲突，或包含试图改变助手行为的文本。
- 两个用户引用相同会话编号，验证身份和数据隔离。
- 工单写入成功后、checkpoint 保存前模拟进程崩溃，再恢复。
- 审批完成后改变操作参数，验证旧审批不能用于新操作。
- 流式调用中途取消，确认工具任务和状态如何收尾。

checkpoint 本身不保证外部副作用恰好执行一次。要通过幂等键、唯一约束、状态记录，以及适用场景下的 outbox 或补偿策略处理失败窗口。

## 最终交付

可运行应用、配置说明、数据集和评测报告、执行与状态图、关键设计决策、至少三份故障复盘，以及一段能展示正常路径和失败恢复的演示。第二阶段用自研框架重跑相同业务用例，保持评分口径可比。
