## 三句话速记

1. 一轮模型响应可以提出多个工具调用，所以交互轮数与工具执行总量需要分别计算。
2. 工具总量预算为一次任务设置累计执行上限，让动态探索的资源消耗有边界。
3. 是否另设预算取决于业务约束和已有工作量上界；次数限制仍需按场景配合时间、并发、费用和收尾策略。

这是本次讨论的复述草稿，尚不代表本人已能独立解释。

## 我的疑问从哪里来

我已经接触两项控制：`ToolCallBudget` 限制工具执行尝试，`FunctionInvokingChatClient.MaximumIterationsPerRequest` 控制自动工具交互循环。看到它们都在限制 Agent 的执行，很自然地需要判断是否重复建设。

当时的原问题：

> FunctionInvokingChatClient的MaximumIterationsPerRequest是代表最大tool调用次数，这个是2，那LLM最多调用就是3次了是吧？后期是不是toolcallbudget可以省略了，使用MaximumIterationsPerRequest控制即可了

进一步追问：

> 从实际Agent架构出发，为什么Agent一般要增加对工具总调用次数的预算限制

这两问包含一个值得保留的判断方向：了解参数的行为之后，还要说明它解决什么实际问题，以及新增机制的收益是否足够。这里记录的是探索中的假设，不将提问改写为本人已经认定的结论。

| --- | --- | --- |

这与我此前提出的“硬限制必须通过运行时代码实现”相衔接：模型可以看到错误并解释限制，是否继续执行仍由运行时控制。

## 我如何理解这个设计

设想故障排查助手后续扩展的场景：先查 `order-api`，再查依赖、检索日志，遇到失败后换参数继续尝试。每一步可能看起来合理，但整个任务的工作量可能不断增加。工具总量预算提供一个累计边界，让应用能够明确承诺“本次任务最多准许多少次执行尝试”。

| 希望解决的问题 | 总量预算的作用 | 还需考虑什么 |
| --- | --- | --- |
| 成本不可控 | 限制付费查询、计算等动作的累计尝试 | 工具成本差异大时，使用分类、加权或费用预算 |
| 对依赖派发过多工作 | 限制一个任务的累计请求机会 | 瞬时压力由并发上限、速率限制等控制 |
| 反复尝试却没有进展 | 在有限尝试后触发收尾策略 | 次数不判断进展，仍可补充无进展检测 |
| 一个任务占用过多共享资源 | 为任务设置可消耗份额 | 多用户场景仍需租户配额和调度 |

“次数”只是资源消耗的近似指标。一次工具调用可能批量读取大量数据，也可能在内部重试多次。因此，限制工具总次数并不直接保证 HTTP 请求数、金额或总时长也受同一个数字约束。机制与来源见 [预算知识卡片](../knowledge/04-budgets-and-termination.md#为什么实际架构会设置工具总量预算)。

## 我会怎样做工程判断

以下判断清单是待本人确认的设计草稿，尚未作为完整运行时实现。

**先问要限制什么。** 如果要求“一次任务最多准许两次工具执行尝试”，就应在实际工具执行前统一准入。当前项目已经这样计数：准许后业务失败也扣额；预算拒绝不继续增加已用额度。并发时要原子地检查并占用，读取 `Used` 的观测值不能代替准入操作。

**再问预算属于谁。** 当前练习以一次运行为作用域，同一运行里的工具共享额度。未来引入子 Agent 时，也要明确子任务如何计入顶层额度，不能通过不断创建新预算绕过任务限制。统一执行入口与任务上下文是后续设计方向。

**判断是否真的需要独立计数。** 动态探索、付费工具和共享依赖使总量预算更有价值。对于步骤固定、全部分支与重试均有已知上界的流程，如果已有控制已满足业务总量要求，可以省略重复的计数器。省略前应能够计算工作量上界，而不是仅凭某个配置名称判断。

**次数不够表达成本时再细化。** 轻量查状态与大规模计算不宜总按相同费用估计。可按工具类别设额度或预占估算成本、执行后结算；能否严格控制金额取决于成本估算和执行边界。这些是方案候选，当前项目未实现，也不需要现在全部加入。

**为耗尽定义结果。** 运行时停止派发超出额度的工作，记录受限原因，保留已有证据与未完成部分。若允许一次模型总结，需要事先留出模型资源，并明确接下来是否终止任务或转人工。当前返回 `TOOL_BUDGET_EXCEEDED` 不会自动完成上述收尾；循环结束也不等于任务成功。

限额应结合正常任务调用分布、成功率、成本和依赖容量确定。练习中的 `2` 用于展示机制，不是生产默认推荐值。

## 用反例检验理解

**说明性假设，未作为新实验运行：** 在已核对的 Extensions 10.10.0 简单调用路径中，轮数配置为 2，模型前两次响应各提出 3 个可执行的函数调用，最后一次在移除函数工具后返回文字。

| 内层模型客户端请求 | 提出的函数调用 | 未设置总量预算时执行 | 总量预算为 2 时获准执行 |
| --- | --- | --- | --- |
| 第 1 次 | 3 个 | 3 次 | 2 次，其余拒绝 |
| 第 2 次 | 3 个 | 3 次 | 0 次，全部拒绝 |
| 第 3 次 | 无，返回文字 | 0 次 | 0 次 |
| 合计 | 6 个 | 6 次 | 2 次 |

右列假定收到拒绝后仍继续这段脚本交互，没有额外的宿主提前终止策略。它说明：执行预算可以阻止执行，但不能单独阻止后续模型请求。串行执行这些调用同样会遇到总量问题，因此串行配置不能替代预算。

这里的“最多 3 次内层客户端请求”依赖已核对的包版本与调用路径；模型提前给出最终答复时可以更少。它不等于经过 SDK、网关和上游重试后的实际 HTTP 请求总量。源码与实验边界见 [机制卡片](../knowledge/04-budgets-and-termination.md#当前应用中的不同边界)。

## 后续追问：模型不知道轮数上限，框架怎样收尾

2026-11-16，本人进一步提问：

> 虽然使用MaximumIterationsPerRequest限制了最大工具执行轮数，但LLM并不知道，在LLM返回tool调用时，如果已经达到最大预算限制，FunctionInvokingChatClient是如何处理的，返回什么信息给LLM来引导LLM不要继续调用了

助手核对当前版本源码后的解释，待本人确认：框架在达到上限后的那次请求之前移除函数工具声明，再把已有交互结果交给模型。该分支没有专门追加“预算耗尽”的说明，也不生成我们自定义的超限错误码。模型获得一次回答机会，但并不知道配置值或工具被撤下的原因。

如果最后一次响应仍提出函数调用，运行时也不执行它，而是结束循环并将响应交回调用方。这让我需要进一步区分：**模型在请求中可用的工具、运行时是否准许执行、模型是否知道停止原因**。第三项是回答体验的设计需求，需要应用显式传达；前两项负责执行边界，不能依赖模型自行理解上限。

复习追问：移除函数工具后，是否就能保证拿到完整的最终答案？不能；执行被限制与答复满足业务要求要分别验证。详细调用次序、`ToolMode=null` 的条件及源码定位见 [达到轮数上限后模型收到什么](../knowledge/04-budgets-and-termination.md#达到轮数上限后模型收到什么)。本次只核对源码，未执行“最后一次仍返回调用”的反例实验。

### 再追问：工具是否最初就注入了历史

本人原问题：

> 请求前移除函数工具声明，是指从历史上下文中移除吗？工具应该是再最初的历史上下文中注入的

助手归纳，待本人确认：这里需要区分“模型可利用的全部输入信息”与“客户端保存的历史消息”。工具声明属于本次请求的工具配置；曾经发生的调用及其结果属于历史。当前应用在 `ChatOptions.Tools` 注册一次工具，之后客户端按每次请求的 options 生成工具配置。

轮数耗尽时，框架克隆 options 并去掉函数声明，没有删除历史调用、结果或 Instructions 中的文字。因此模型可能仍知道工具名称；“记得这个工具”和“本次请求仍提供它”不能等同。机制、适配器版本与源码见 [工具声明与历史上下文](../knowledge/04-budgets-and-termination.md#工具声明与历史上下文有什么区别)。

复习追问：如果自行在系统提示中写了“可以调用 GetServiceHealth”，移除 `Tools` 会把这句话也删掉吗？不会。提示中的描述、请求里的声明和运行时实际执行仍需要分别判断。上述解释来自本轮静态源码核对，尚无本人复述或 Magpie 请求抓包证据。

### 本人纠正：工具声明本来也是模型上下文

本人指出：

> 不是啊，工具声明不是通过上下文提供给LLM的吗？类似System Prompt一样，你要移除，也是从上下文中移除了工具声明把

这一纠正成立：这里讨论的是模型本次可利用的上下文，工具声明属于其中的信息；移除声明，可以理解为从本次上下文中移除这部分能力说明。助手此前过度强调 API 字段与历史消息的区别，没有正面回应这个层次。

修正后的表达：**收尾请求不再向模型提供这些函数声明，过去的调用与结果仍可供参考。**至于声明具体编码在哪种提示模板或模型输入结构里，是服务端实现细节，本次没有验证。这条本人表达作为“工具声明属于广义上下文”的概念理解证据保存，不推定整个预算主题已掌握。

### 继续追问：声明的位置和角色由谁决定

本人原问题：

> MAF实现方式，时把可用工具声明放在最后提供给LLM的吗？如果是的话，这部分内容是不是已System的角色提供的？

助手澄清，待本人确认：此前“系统指令 + 历史 + 工具声明”的排列只是列出组成，不能据此认为声明在最终模型输入的末尾。当前 Responses 适配器将函数声明转换为独立的 FunctionTool，没有把它构造成 System 消息。声明在 API 层没有消息 role。

新的判断边界是：**属于模型上下文，不等于一定以 System 消息表示；请求字段的位置，也不等于模型 token 的位置。**最终编码方式需要查看网关和上游服务，现有客户端源码不能证明。详细依据见机制卡片的“工具声明是否放在最后并以 System 角色发送”小节。本次未新增模型或网关实验。

本人随后询问 HTTP 接口是否本身就分开接收指令、输入与工具，并继续问 OpenAI 兼容接口的情况。助手按常见的 Chat Completions 接口补充对照，待本人确认：指令通常放入带角色的 messages，函数声明仍独立放在 tools；它比 Responses 的函数声明多一层 function 包装。执行后的 role: tool 消息是结果，不是声明。

这项对照用于检查理解是否能跨协议迁移：**先找请求的指令、历史、声明和结果分别在哪里，再判断运行时修改了哪部分。**“OpenAI 兼容”不能单独确定 API 路径或服务端模型模板。已补充机制卡片的协议对照，尚未进行真实 Chat Completions 调用或本人迁移验收。

### 延伸：API 字段怎样真正进入模型

本人继续追问：

> api是分成不同属性传递的，LLM后台是如何组合的呢？然后传递给推理引擎进行推理的?

助手整理，待本人确认：常见文本推理服务先解析请求，再按模型对应的 Chat Template 组织指令、历史和工具说明，编码为 token ID，配合生成参数交给引擎；输出经过解码和工具解析后，才成为 API 的结构化结果。工具实际执行又是下一层运行时职责。

本次查看的 Qwen2.5 官方模板将工具说明写进开头的 system 段。这为我此前提出的“工具说明也会进入类似 System Prompt 的上下文”提供了一个具体实例；它不代表当前 GLM 服务采用同样模板。值得保留的认识是：**API 表示、模型输入格式、执行权限是不同层次；说明一个层次时，不能否定另一个层次上的正确直觉。**

机制、示意与待做实验集中在 [从 API 字段到模型输入与推理](../knowledge/05-api-to-model-input.md)，这里保留个人问题和判断变化。尚未执行模板渲染或本人复述验收。

## 复习自测

先用自己的话作答，再展开对应答案。参考答案均由助手整理。

1. 轮数配置为 2，是否能保证工具最多执行 2 次？用一个反例解释，串行执行会改变结论吗？

<details>
<summary>展开第 1 题参考答案</summary>

不能。一轮可提出多个工具调用，例如上述两轮各三个调用，共六次。串行只改变同轮执行方式。若业务还要求整个任务最多准许两次执行，需要在执行边界落实总量约束。上表是推演，不是本次运行证据。

</details>

2. 若要求“一次任务最多花费一定金额、同时最多两个外部请求”，工具总次数预算足够吗？一次工具内有三次 HTTP 重试又怎么算？

<details>
<summary>展开第 2 题参考答案</summary>

不足。金额需按实际计费对象估算和核算；同时在途请求数需在合适的派发层限制并发。工具准入只看到一次执行时，内部三次 HTTP 尝试并不会自动成为三次工具扣额，重试与外部请求量需要在对应层控制。即使外层只准许一次工具调用，内部批量或并发请求仍可能很多。

</details>

3. 已获准的查询超时，应该退还次数吗？把 `TOOL_BUDGET_EXCEEDED` 返回给模型之后，任务是否已经终止？

<details>
<summary>展开第 3 题参考答案</summary>

当前预算计量的是获准的执行尝试，超时也消耗一次；退还可能让持续失败绕过尝试上限。若业务采用别的计量方式，应另定义契约。超时只证明没有及时取得结果，不能据此推断服务健康状态。

超限错误只是业务结果。当前框架不会因为该 JSON 字段自动实施宿主终止策略；仍需运行时代码决定是否继续模型交互、预留总结额度并记录受限原因。

</details>

4. 某固定流程最多执行三个步骤，每步最多两次外部尝试，还必须再加一个工具计数器吗？如果改成可动态创建子 Agent 呢？

<details>
<summary>展开第 4 题参考答案</summary>

若无隐藏分支、循环或重试，且计量对象确实是这些尝试，已有最多六次的上界；业务接受该上界时，独立计数器可以省略。不能把六次外部尝试直接当成六次框架工具调用，要核对执行边界。

允许动态创建子 Agent 后，上界可能失效，应重新计算总工作量，并明确任务共享额度或子预算如何受顶层总量约束。不能仅限制每个子 Agent，再允许无限创建子任务。

</details>

## 两分钟面试表达

以下为助手整理的参考稿，待本人用自己的话复述；不得将设计建议当作已经落地的项目经历。

> 我会先明确计量对象。轮数控制模型与工具交互的循环，一轮可以请求多个工具，所以轮数与工具执行总量不能直接等同。自主 Agent 的探索路径会动态变化，工具总量预算能限制单个任务的累计工作，帮助控制成本、依赖负载和无效尝试。
>
> 在这个学习项目中，工具预算在执行前准入，获准后的业务失败也扣额；已有确定性检查覆盖重复查询、更换服务、失败扣额和并发准入。并发检查只验证预算对象，不能当作模型循环验证。普通 loop-check 已提交正常与失败实验输出，流式循环也已验证；运行结果的机制解释还需要独立复述。
>
> 工程上还要考虑成本差异、工具内部重试，以及额度耗尽后的宿主收尾。次数上限不替代并发、费用或授权控制。固定流程若已有满足需求的工作量上界，可以省略重复计数；动态多工具或子任务执行则需要重新检查整体资源边界。
