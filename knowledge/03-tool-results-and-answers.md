# 工具结果与最终回答

关联课程：L02。来源：2026-11-09 用户提交的两次 Magpie Responses 工具调用日志，以及本地 `Program.cs`、`ServiceTools.cs` 和快照文件。

## 分开判断三个结果

| 层次 | 判断什么 | 本次 billing-api 结果 |
| --- | --- | --- |
| 工具执行 | 是否实际调用了目标 C# 函数并返回结果 | 日志显示 GetServiceHealth 执行并返回 JSON |
| 业务查询 | 是否找到用户需要的数据 | 返回 ok=false、UNKNOWN_SERVICE，属于已处理的业务未找到结果 |
| 最终回答 | 是否准确表达工具结果及其缺失信息 | 正确报告未知服务，但错误地将 errorCode 字段称为证据编号 |

`UNKNOWN_SERVICE` 不需要被包装成程序崩溃；工具可以正常执行并返回业务失败信息。完成原因 `stop` 也只描述模型生成结束，不能证明业务查询成功或回答正确。

## 字段有不同语义

- `errorCode` 表示错误类别，例如 UNKNOWN_SERVICE；它不是唯一证据编号。
- `evidenceId` 在这个学习数据中指向一条快照证据，例如 snapshot-order-001。
- 字段名本身不是证据 ID。可以说“依据是工具返回了 UNKNOWN_SERVICE”，但不能把错误码或字段名填到证据编号的位置。
- 未返回的字段应省略或明确标为未提供，不能为了填满回答格式而补造。

## 提示词与输出验证

原示例要求回答保留状态、时间和证据编号，却没有限定只对成功结果适用。对失败分支应另行约定：报告服务 ID 和错误码，并如实说明没有查到健康数据。

这项提示词修正可以改善行为，但是否改善需要固定模型、问题和工具返回后对照验证。对于必须严格一致的字段，可由宿主代码直接渲染，或将模型输出结构化后与工具结果比对；格式合法仍不意味着字段语义正确。

## 本次日志中的其他边界

两次提交的终端记录各显示一次 `[tool-call]` 和一次 `[tool-result]`。470 和 401 是程序累计的 Agent 更新对象数量，不是工具执行次数，也不能直接据此推算 HTTP 请求数量。

`observedAt` 是快照的观测时间，本次为 2026-11-06T06:00:00Z；之后调用工具不会让这份快照自动变成新的实时观测。

源 JSON 包含 metrics，但当前函数没有将它们放入工具返回。因此模型本轮没有从该工具结果收到这些指标。分析信息是否充足时，要检查模型实际收到的结果，而不只是磁盘文件有什么。
