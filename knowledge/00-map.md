| 层次 | 必须理解的内容 | 用来检验理解的实验 |
| --- | --- | --- |
| 模型基础 | token、上下文窗口、采样、延迟、用量、角色和消息内容 | 相同输入重复运行；截断上下文；比较输入增长后的成本 |

| 工具系统 | 描述和 schema、类型验证、错误分类、并发、超时、幂等 | 未知工具、越界参数、重复请求、依赖工具并行错误 |
| 上下文工程 | 指令、当前任务、检索证据、历史、工具结果、摘要 | 比较全量历史、滑动窗口和摘要造成的信息损失 |
| 状态与记忆 | 会话历史、业务状态、长期偏好、持久化、隔离和删除 | 重启恢复；同一用户多会话；跨用户访问检查 |
| 检索与知识 | chunk、embedding、关键词/向量/混合检索、rerank、证据版本 | 找到召回失败和生成失败各一个，分别修复 |
| 编排与协作 | 固定流程、自主循环、路由、顺序、并行、handoff、角色分工 | 同一任务比较单 Agent、工作流、多个 Agent |
| 可靠性 | 取消、超时、重试、退避、限流、checkpoint、副作用恢复 | 每个持久化与工具执行边界分别注入故障 |
| 可观测与评估 | trace/span、事件、用量、成功率、回归、成本与质量权衡 | 从一次失败 trace 找到原因，并加入回归用例 |
| 权限与隔离 | 身份、租户、工具白名单、审批绑定、提示注入、敏感信息 | 恶意文档、越权工具请求、审批后改参 |
| 协议与平台 | provider 适配、MCP、A2A、API 宿主、任务调度 | 新增工具服务和 provider，记录无法统一的能力 |

## 首先分清的边界

- **LLM 调用**根据输入产生输出；**Agent 运行时**组织消息、工具执行和循环控制；**业务应用**定义数据、权限和成功条件。
- **RAG**是检索证据并参与生成的方法，可以用于单次调用，也可以作为 Agent 的工具。
- **工作流**显式表达执行路径；其中某个节点可以是 Agent，也可以是普通函数。
- **会话历史**保存交互内容；**业务状态**表示任务进展。二者可能一起持久化，但职责不同。
- **结构化输出**约束形式；**事实和业务验证**判断内容是否可信和可执行。
- **模型请求动作**不等于动作已获授权，也不等于工具已经执行成功。
- **MCP**解决工具和资源接入的一类协议问题；它不自动解决业务权限、评测和恢复。
- **框架支持某能力**不等于应用已经正确配置并验证了该能力。

这些边界将通过代码和实验逐个落实。MAF 的 Agent、工作流、会话和上下文提供器可作为对应入口。[官方概览](https://learn.microsoft.com/en-us/agent-framework/overview/)

## 知识卡片要求

每课最多新增 1–3 张卡片，先写自己的解释，再补参考资料。每张卡至少有一个反例、一个实验或源码位置、一个适用条件。不要把 API 清单当成知识总结，也不要用无法验证的“模型自己理解了”代替执行机制。

对论文和其他框架的扩展阅读安排在具体问题出现之后。正式阅读时核对原论文和当前官方实现，记录“理论模式”“框架实现”“本项目选择”三者的差别。
