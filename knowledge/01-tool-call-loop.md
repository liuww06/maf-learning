# 工具调用与 Agent 执行循环

状态：助手提供的首讲材料；用户已口述解释超时反馈与运行时强制限制，计数范围和实现能力待验收。关联课程：L00。

## 核心机制

在本地 C# 函数工具场景中，模型生成工具调用请求，应用中的运行时接收请求并执行已注册的函数，再把工具结果交给模型。模型返回工具请求时，不代表函数已经执行，也不代表操作已经获得授权。

业务代码提供工具实现、数据访问和权限规则；框架帮助组织模型调用、工具分发和消息反馈。业务授权必须由可信代码实施，不能只写在提示词里。

## 一个教学示例

用户询问订单服务是否健康。应用向模型提供用户问题以及 `GetServiceHealth` 的名称、描述和参数定义。模型可能返回类似下面的调用请求：

```json
{
  "callId": "call_001",
  "name": "GetServiceHealth",
  "arguments": { "serviceId": "order-api" }
}
```

这是简化的教学表示，不对应特定 provider 的完整 wire format，也不是一次真实模型调用记录。

运行时检查工具是否存在和参数是否合法，结合应用的身份与权限规则决定是否执行，再调用 C# 工具。工具从练习快照读取 `order-api` 的 `degraded` 状态和观测时间 `2026-11-06T06:00:00Z`。

运行时把模型的调用消息及对应工具结果加入对话，通过调用 ID 保持关联，再请求模型生成解释。最终回答应说明结果来自固定练习快照，不能冒充实时查询。

## 一次应用调用与多次模型请求

一次应用层运行可以包含多次模型请求。在这个例子中，第一次模型请求用于产生工具调用，第二次用于结合工具结果形成回答。复杂任务可能有多轮工具交互，也可能不需要工具。

最小运行时要区分成功完成、等待人工输入、错误、取消和超限。模型产生正常结束的最终答复可以结束当前任务；达到最大轮数、超时或预算上限是另一种终止原因，不能统一记为成功。

## 反例

模型提出查询 `billing-api`，而数据集中没有该服务。这属于业务数据查找失败：工具可以返回明确的“未知服务”结果，由运行时按既定错误策略处理并视情况交回模型。它不等于服务健康，也不必然证明模型调用参数的类型不合法。

## 查询超时的反馈

用户已提出：运行时应如实向模型反馈超时，模型无法凭此确定服务状态，可以给出进一步排查建议。这说明已初步理解失败反馈与证据不足的关系，尚未进行代码验证。

需要进一步区分两个状态：查询工具的执行结果是 `timeout`，被查询服务的健康状态是 `unknown`。通用的查询超时本身不能证明发生在建立连接阶段，也不能证明被查询服务宕机；需要日志或其他观测来判断原因。

我们可以在应用中明确设计如下错误结果，作为反馈给模型的教学格式：

```json
{
  "callId": "call_001",
  "executionStatus": "timeout",
  "serviceHealth": "unknown",
  "data": null,
  "errorCode": "TOOL_TIMEOUT"
}
```

这是拟定的应用契约，不是 MAF 自动生成的标准结构。实现时需要明确捕获哪些可处理错误、怎样保留调用关联，以及哪些错误应终止任务。对用户的结论应说明本次未取得结果，网络、依赖或服务负载等只能作为待排查方向。

## 重试限制与运行预算

用户已明确指出，重试上限是硬性限制，必须通过运行时代码实施，不能依靠上下文提示词保证。提示词仍可以说明约束，帮助模型安排动作；实际执行前必须由可信代码检查预算。

“最多重试两次”在本练习中表示首次尝试加两次额外尝试，最多执行三次。还需要明确计数范围：仅在工具函数内部设置局部重试计数，无法阻止模型再次发起新的工具请求；新的 `callId` 也不能使同一逻辑操作重新获得预算。

本练习可把任务内的这次指定服务查询标识为一个逻辑操作，并在运行状态中维护其尝试次数。同时维护整个任务的工具调用总量和模型轮数预算，以覆盖模型更换参数或工具的情况。逻辑操作身份由应用定义，不能把所有相同参数的合法后续查询永久视为同一次操作。

以下只是假设的教学策略，不是 MAF 默认配置或 API 定义：

| 范围 | 示例限制 | 要解决的问题 |
| --- | --- | --- |
| 本次逻辑查询 | 最多尝试 3 次 | 失败后重复执行同一查询 |
| 整个任务 | 工具执行总量最多 10 次，模型请求最多 8 轮 | 反复发起新调用或更换工具 |
| 整个任务 | 30 秒期限 | 到期停止派发新调用，并向进行中的操作传递取消 |

预算耗尽是明确的终止原因，不应记成任务成功。是否允许一次受限的最终总结请求，也应事先纳入预算策略。取消请求不保证任意下游操作立即停止，后续实现时必须验证工具的取消行为。

这些计数策略尚未完成个人实现或故障实验。后续已确认 Magpie Responses 接入，实际调用见 [L01 记录](../progress/2026-11-06-l01.md)；逻辑操作的计数范围与执行控制会在 L02 和后续可靠性课程中验证。
